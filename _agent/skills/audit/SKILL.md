# 🔍 規格庫巡檢與除舊佈新 (Audit Docs)

> **觸發時機**：定期大保養、覺得文件與程式碼脫節、或使用者明確呼叫 `/audit` 時執行。

當你被呼叫 `/audit` 時，你的任務是扮演**QA 與技術文檔維護者**，找出系統現況與規格書之間的裂痕。請執行以下步驟：

## 步驟一：讀取現有設計與實作
1. 開啟並詳細閱讀 `docs/網站功能規格書.md`。
2. 掃描 `src/` 目錄下最核心的 UI 相關元件與頁面（如 Header, MainMenu, QuizView, Theme/CSS 等）。
3. 檢查 `src/data/config.ts` 中的主題、顏色與全域設定。

## 步驟二：交叉比對尋找矛盾
仔細對照「規格書中的描述」與「實際程式碼的實作」，尋找以下不一致之處：
- **顏色/色碼**：規格書寫的顏色跟 `index.css` 或 `config.ts` 不一樣。
- **元件行為**：規格書寫有某個按鈕或提示，但程式碼裡已經拿掉了。
- **邏輯邊界**：規格書提到的 localStorage key 或資料處理邏輯，與 `utils/storage.ts` 或 API 呼叫不符。
- **遺漏防呆**：程式碼裡寫了詳細的防呆或狀態處理，但規格書完全沒提到。

## 步驟三：整理差異並向使用者請示
**不要直接修改規格書**。請先彙整比對結果，並使用工具向使用者發送一份「稽核報告」：

提供一份清晰的列表，例如：
1. **[顏色矛盾]** 規格書寫康軒主色是 `A`，但程式碼是 `B`。
2. **[行為遺失]** 規格書提到「有清除所有紀錄按鈕」，但 UI 上找不到這個元件。
3. **[文件缺漏]** 程式碼中新增了深色模式 (`.dark` hook)，但規格書的第五章未完整列出相關變數。

## 步驟四：等待確認後同步更新
在報告中詢問使用者：「請問針對以上矛盾，**要以程式碼為準，還是以規格書的定義為準去改程式碼？**」

得到使用者明確指示後：
- 若以**程式碼為準** → 修改 `docs/網站功能規格書.md`，將矛盾的舊規定刪除覆寫。
- 若以**規格書為準** → 修改對應的 `src/` 程式碼組件，將行為還原為規格書的定義。 
- 若有不需要的過期開發文件（例如散落在各處的舊 plan.md 等），也可向使用者建議刪除，保持環境整潔。
