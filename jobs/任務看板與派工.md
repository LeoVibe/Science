## 三、派工規範 (Assignment Protocol)

### 3.1 命名格式
```
jobs/JOB-{數字編號}-{發起者縮寫}-{描述}.md
```
- **發起者縮寫 (Origin)**：
  - `AG`：由 Antigravity (AI PM) 根據進度或除錯需求主動發起。
  - `USER`：由大 PM (使用者) 直接指派或提出的需求。
  - `DEV`：由開發端 (Cursor) 在執行中發現並提出的技術擴編。
- **範例**：`JOB-033-USER-Refine-G3-Chinese.md`

### 3.2 派工單必備欄位
| 區塊 | 內容 |
|------|------|
| **任務背景** | 為什麼要做、解決什麼問題 |
| **任務詳情** | 具體步驟、影響檔案路徑 |
| **關鍵參考檔案** | 開發前必須閱讀的檔案清單（表格形式） |
| **執行規範** | 開單防呆流程指向 `_agent/skills/dojob/SKILL.md`，工程與 UI 規範指向 `_agent/skills/webdev/SKILL.md` |
| **驗證基準 (DoD)** | 核取清單，明確定義「完成」的標準 |
| **撰寫紀錄** | 必須在文件最上方標註：`*Created by {AG/Cursor} at YYYY-MM-DD HH:mm*` 與 `*Last Updated at YYYY-MM-DD HH:mm ({更新者與事由})*` |

### 3.3 Cursor 指令範本
派工單**不需要**內嵌 Cursor 指令。AG 在對話中直接提供使用者一段**第一人稱**指令：

```
今日任務：{一句話摘要}。
請詳細閱讀並依據 `jobs/JOB-XXX-*.md` 的規格進行開發，
協作與開發規範請遵循 `_agent/skills/webdev/SKILL.md`，開結案一律聽從 `_agent/skills/dojob/SKILL.md`。
完工後請執行單元測試，並將成果與測試紀錄寫入 `jobs/JOB-XXX-Report.md`，
交回給 AG 進行最終測試。
```

### 4.3 禁止事項
- ❌ 嚴禁在根目錄或 `codex/` 產生 `task_assignment_*.md` 等拋棄式回報文件
- ❌ 嚴禁繞過 `jobs/` 目錄自行選擇回報路徑
- ❌ 嚴禁修改不在派工單影響範圍內的檔案（除非提前告知 PM）
- ❌ 嚴禁在**專案根目錄**放置一次性除錯腳本（如 `test.js`、`debug.js`、`tmp_*.js`）。臨時測試檔請放在 `scripts/` 或 `tests/` 目錄下，且完工後必須清除或加入 `.gitignore`，**絕對不可隨正式程式碼一起 commit**
- ❌ **嚴禁未經 PM 許可，自行在專案第一階層（根目錄）建立任何新目錄或隱藏目錄（例如 `.logs/`）**。所有生成的報告或日誌，必須放進既有的 `docs/reports/` 或相關功能目錄下。
- ❌ 嚴禁在程式碼中寫死**個人絕對路徑**（如 `/Users/xxx/...`），必須使用相對路徑或環境變數

## 五、AG 驗收與結案機制 (Verification & Closing)
當執行者（如 Cursor）回報「已完成」並產出完工報告時，AG 進入 `VERIFICATION` 模式：

1. **白箱檢查**：讀取修正後的原始碼，確保邏輯正確。
2. **標準對齊**：對照「派工單」中的 **DoD (驗證基準)** 逐條勾選。
3. **運行驗證**：執行腳本或啟動環境確認功能符合預期。
4. **最終裁判與結案 (Closing Ceremony)**：
   - ✅ **驗收通過**：**由驗證者 (AG/PM)** 手動在本看板中將狀態標記為 **`🟢 DONE`**。這才算正式「結案」。
   - ⚠️ **驗收失敗**：產出「修正建議清單」，交回執行者重新處理。

### 5.1 若任務由 AG (PM) 親自執行時
當任務編號為 `JOB-AG-XXX` 且由 AG 本人執行（如：課綱研究、高品質題庫生成）時，流程同樣遵循透明化原則：
- **一樣會產出報告**：AG 會產出 `Report.md` 或對應的 `knowledge/` 文件作為執行證據。
- **由使用者 (大 PM) 驗收**：AG 會透過對話與 `notify_user` 展示成果，請使用者進行感官或方向性的最終確認。
- **標記結案**：確認無誤後，AG 會同步更新看板為 `🟢 DONE`，確保所有工作都有跡可循。
