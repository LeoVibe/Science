# JOB-122-USER-國語科研究階段重建與題庫擴充（G3-G6 S2）

**`job_type`**: `research_verification + content_production`
**預計 API 消耗**：2500-3000 RPD（Gemini-3.1-Flash-Lite / Yotta 金鑰）

> 執行架構：USER 定義 → Antigravity 驗證（階段一）→  
> Claude Code 審視決策 → Cursor/Antigravity 擴充（階段二）→ Report

---

## 📌 任務背景

G3-G6 S2 國語科研究層因前次（JOB-116）出現大規模品質問題：
- 網址失效率 ~30%
- 轉義編碼錯誤（%3D）
- 引用不穩定學校連結

本任務分兩階段重建，建立穩固的知識地基：
1. **驗證階段**：確認既有 KL4 檔案完整性  
2. **擴充階段**：基於完整 KL4，進行題庫出題與驗證

---

## 🎯 任務目標

1. ✅ 確保 G3-G6 S2 國語 KL4 雙檔完整性 ≥ 95%（缺漏率 ≤ 5%）
2. ✅ G3 S2 題庫擴充至 25+ 題/課（翰林/康軒/南一 三版本全部）
3. ✅ 新增題目 CQI-P ≥ 5.5，blind_eval Match Rate ≥ 85%

---

## 📖 執行範圍

### 階段一：研究驗證（KL4 檔案盤點）

**掃描目標：**
```
知識/課綱研究/國語/
├─ 三下/  (G3 S2)
│  ├─ 翰林/
│  ├─ 康軒/
│  └─ 南一/
├─ 四下/  (G4 S2)
├─ 五下/  (G5 S2)
└─ 六下/  (G6 S2)
```

**驗證項目：**
- [ ] KL3 檔案存在且有效（文本分析）
- [ ] KL4 主檔存在且有效（語法、考古題分析）
- [ ] KL4 副檔存在且完整（誘答機制、學生迷思）
- [ ] 所有 URL 連結可達（角括號包裹，防碼）

**預期交付：**
- `jobs/JOB-122-Verification-Report.md`
  - 完整課次清單（G3-G6 全級別）
  - 缺漏課次清單 + 網址失效統計 + 優先度排序
  - 修復建議

### 階段二：題庫擴充（待階段一 ≤ 5% 缺漏通過）

**執行範圍（首批）：**
- **G3 S2 國語三版本**（翰林/康軒/南一）
- 12 課 × 3 版本 = 36 課檔案

**出題原則：**
1. 每課以 KL4 副檔「誘答機制」為依據進行出題
2. 目標：各課現況 20~25 題 → 擴充至 25+ 題
3. 新增題目命名規範：`[課號]-ext-[編號]`（如 L1-ext-01, L1-ext-02 等）

**品質卡點：**
- 每新增 10 題執行 blind_eval 驗證
- Match Rate < 85% → 提取 Mismatch 清單 → 回溯修題 → 重測
- CQI-P < 5.5 → 停止出題，報告 Claude Code 決策

**預期交付：**
- `jobs/JOB-122-Production-Report.md`
  - 新增題數統計表（版本 × 課別）
  - 盲測結果彙整（各課 Match Rate、Mismatch 清單）
  - 修題過程記錄（哪些題修改了、原因、驗證後結果）

## 📋 執行步驟

### 階段一：研究驗證（Antigravity Agent 負責）

1. **讀取必要文檔：**
   ```
   - knowledge/README_研究架構總綱.md
   - question/README_出題與品管準則.md
   ```

2. **掃描 KL4 檔案結構：**
   ```bash
   # 掃描 G3-G6 S2 全部課次的 KL3 + KL4 檔案
   find knowledge/1_課綱研究/國語/[三四五六]下/[翰林康軒南一]/ -name "KL*.md" | sort
   ```

3. **驗證每課（偽代碼邏輯）：**
   ```
   for each grade in (G3, G4, G5, G6):
       for each semester in (S2):
           for each publisher in (翰林, 康軒, 南一):
               for each lesson in (L1-L12):
                   check_file_exists(KL3_*.md)
                   check_file_exists(KL4_主檔.md)
                   check_file_exists(KL4_副檔.md)
                   validate_all_urls_in_KL4()
                   report {
                       status: ok | missing | url_broken,
                       lesson: L1,
                       files: [KL3, KL4_主, KL4_副],
                       broken_urls: [URL1, URL2, ...]
                   }
   ```

4. **生成驗證報告：**
   - 按級別統計完整課次、缺漏課次、失效 URL
   - 計算缺漏率百分比
   - 列出優先修復清單

5. **決策卡點判斷：**
   - 若缺漏率 ≤ 5% → **PASS 進階段二**
   - 若缺漏率 > 5% → **FAIL 需補完**，回報 Claude Code 決定後續

### 階段二：題庫擴充（Cursor/Antigravity Agent 負責，待階段一通過）

*此階段由 Claude Code 發起新派工*

1. **選定首批目標：** G3 S2 國語（翰林優先，再依序康軒、南一）

2. **參照 KL4 進行出題：**
   ```bash
   # 開啟對應課檔與 KL4 副檔（誘答分析部分）
   # 基於「學生常見迷思」和「誘答選項邏輯」進行新題出題
   
   # 假設 KL4_副檔.md 中記載：
   # - 常見誤點：學生容易混淆「修辭手法」與「敘事角度」
   # - 誘答邏輯：提供看似正確但實為修辭的選項
   
   # 則新題應設計為：
   # 題幹：「這句話使用了什麼修辭手法？」
   # 正確答案：A) 排比
   # 誘答選項 B)：「視角轉換」(AI 常混淆的點)
   ```

3. **每 10 新題執行盲測：**
   ```bash
   node scripts/run_blind_eval.js question/platform/G3/Chinese/S2/HanLin --force
   ```

4. **處理 Mismatch 題目：**
   - 若 Match Rate < 85%：
     ```
     a) 提取 Mismatch 清單
     b) 分類：AI 計算誤 / AI 無法判斷 / AI 邏輯混淆
     c) 針對性修改：簡化題幹、調整選項、強化正答邏輯
     d) 重新執行盲測驗證
     ```

5. **產出最終報告：**
   - 新增題數統計（版本/課別）
   - 盲測結果彙整表
   - 修題過程日誌

## 🚧 任務邊界（Critical）

### ✅ 只做：

- **驗證 KL4 檔案完整性**
  - 檔案存在性檢查
  - URL 有效性驗證（實際連線測試）
  
- **基於 KL4 副檔進行出題**
  - 遵循「誘答機制」和「學生迷思」邏輯
  - 確保新題與既有題風格一致

- **執行盲測驗證**
  - Match Rate 監控
  - Mismatch 題目識別與回溯修題

- **修改題目與標籤**
  - 更新選項/題幹
  - 修改 review_status 標籤為 `verified` 或 `confirmed`
  - 更新 CQI-P 分數

- **進度記錄與報告**
  - 生成驗證報告、產出報告
  - 每階段檔案清單精確

### ❌ 不做：

- **重寫或重建 KL4 檔案本體**
  - 如需超大幅修改（> 30% 內容），由 USER 決策後另發派工
  - KL4 檔本身通常僅做查閱，不做編輯

- **模型權重調整、自定義參數**
  - 使用 Gemini-3.1-Flash-Lite 預設配置
  - 無需修改提詞或系統角色

- **CQI-P < 5.5 的題目進入版本**
  - 需停止出題並報告 Claude Code
  - 待修正派工完成後再行

- **手工細部編輯**
  - 應盡量自動化處理，避免逐題人工調整
  - 僅例外題目 (Mismatch 清單) 才人工介入
