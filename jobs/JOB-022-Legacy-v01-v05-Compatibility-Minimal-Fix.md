# JOB-022：歷史版 v0.1 / v0.5 可用性修復（最小改動、相容現有題庫）

## 任務背景

目前歷史版入口 `v0.1`、`v0.5` 已存在「可開啟但不可正常使用」問題，影響使用者體驗與版本回顧可信度。  
需求重點為：在**不破壞現有題庫結構**、且以**最小程式改動**前提下，讓使用者仍可完整完成操作流程。

## 任務詳情

1. 現況診斷
   - 釐清 `/history/v0.1/`、`/history/v0.5/` 失效的直接原因（資源路徑、router、資料讀取、執行錯誤等）。
   - 記錄最小重現步驟與影響範圍（首頁、選科、開始作答、提交、結果頁）。

2. 最小改動相容修復（優先採「入口相容橋接」）
   - 方案優先順序：
     1) 保留歷史版網址不變，於入口做相容橋接到可運作流程。  
     2) 若可直接修補舊包資源路徑，則以最小 patch 修復。  
     3) 不採大規模重建舊版 bundle。
   - 需確保使用者能完成至少一輪完整操作：進站 → 選單元 → 作答 → 看結果。
   - 需相容現有題庫（`question/platform` 或已部署對應路徑），不得新增平行題庫格式。

3. 版本資訊與入口一致性
   - 前台更版資訊中的歷史版連結文案需同步調整（若採橋接模式，需明示「相容模式」）。
   - 避免使用者誤以為是完全原樣復刻版，應清楚標示可用性與限制。

## 執行規範

- 協作流程依 `.agent/workflows/webdev.md`。
- 以「可用優先、最小改動」為主，不追求舊版 UI 1:1 完全復刻。
- 不新增題庫雙軌格式；如需轉接，僅做路由/入口層兼容。

## 風險與回滾策略

- 主要風險
  - 歷史版資源若散落且耦合高，直接修補可能擴大維護成本。
  - 相容橋接若文案不清，使用者可能誤解為舊版原生執行。

- 回滾策略
  - 每次修補分小步提交；若不穩定，先回退到「可訪問但顯示維護提示 + 回主站」。
  - 保留歷史版 URL，不破壞外部分享連結。
