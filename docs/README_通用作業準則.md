## 第零章：任務三段式 Checklist

所有 JOB 派工單或 Agent 啟動之任務，**必須同時包含以下三張 Checklist**，缺一不可：

### 1️⃣ 啟動 Checklist (Pre-Flight)
- [ ] 強制讀取的規範文件（列出完整路徑）
- [ ] 前置素材查核（KL3/KL4 存在性 + RM 階段確認）
- [ ] 目標品質等級確認（QL4 or QL3）

### 2️⃣ 驗收 Checklist (Acceptance)
- [ ] CQI-P ≥ 5.5（出題品管通過）
- [ ] CQI-V 盲測 Match Rate ≥ 85%
- [ ] 最終 CQI ≥ 6.5（方可上架）
- [ ] 內容驗證（scenario / explanation 存在）

### 3️⃣ 成果 Checklist (Deliverables)
- [ ] 成果表格填寫完畢（中文課名 / 真實模型 / 執行日期+時間）
- [ ] 題庫進度總表已同步（`docs/進度彙整_題庫研發與產出.md`）
- [ ] 已執行 `/pj_sync`
- [ ] 產出 `jobs/JOB-XXX-Report.md`
- [ ] 結案後已依 **`docs/README_任務派工準則.md` 第六章（階段三：結案）** Discord 項完成摘要同步（`user-discord-relay`／`send_message` 或可貼上摘要）

> 缺此三張 Checklist 的派工單不得進入執行階段。

### Checklist 使用規則

1. **禁止預先全部打勾**：每一項必須在實際完成後才能打勾。
2. **驗收項目需佐證**：Acceptance Checklist 的每一項打勾時，必須在旁邊填入實際數值或佐證描述（例：CQI-P 實際值 5.8）。不可只打勾不說明。
3. **Deliverables 禁止模糊描述**：Report 的異動清單必須列出實際檔案路徑。禁止填寫「歷史變更」「如上」「見程式碼」「已合併」等無資訊量的文字。
4. **結案驗收由第三方確認**：Report 的「驗收確認」欄位由執行者以外的人填寫，執行者不得自行填入「通過」。

## 第一章：雙軌制協作架構

### 1.0 角色分工（Multi-Agent）

| 角色 | 擔當者 | 職責 | 禁止事項 |
|:--|:--|:--|:--|
| **PM / 總架構師** | Claude Code | 規劃、派工、驗收、`/pj_sync` | 禁止直接執行出題/盲測/腳本跑批 |
| **執行工程師** | Cursor / Gemini | 讀取派工單、按 DoD 執行、撰寫 Report | 禁止自行開派工單或修改規範 |
| **QA / 稽核** | Codex / Antigravity | 跨檔一致性檢查、驗證數據 | — |
| **使用者** | 人類 | 最終決策、核准草稿、驗收 Report | — |

Claude Code **規劃任務但不動手執行**，就像建築師畫藍圖但不搬磚。
使用者明確授權例外時，須在派工單標注 `executor: Claude Code（使用者授權例外）`。

### 1.1 技能檔 vs 知識檔

| 類型 | 位置 | 職責 |
|:--|:--|:--|
| 技能檔 (`_agent/skills/`) | **薄層觸發器**：觸發條件 + 權威指向 + 硬閘，≤ 15 行 | 不解釋理論 |
| 知識檔 (`knowledge/`, `question/`, `docs/`) | 原理與規範正文 | 被 Skill 引用 |

Skill 檔案只能使用強連結指向知識檔，**嚴禁在 Skill 中長篇大論解釋原理**。
Skill 的設計原則：Controller 層（CLAUDE.md + docs/）管安全與角色，Skill 只管觸發路由。

### 1.2 任務啟動三大時機

1. **PLANNING 模式**：涉及 3+ 檔案異動 → 先建 JOB 派工單
2. **生產環境部署**：禁止無派工單部署
3. **進度/結案詢問**：回報前必建 Report.md

### 1.3 許可機制
無使用者明確許可（LGTM / 允准 / 開始執行），**禁止進入 EXECUTION 階段**。

### 1.4 任務邊界守則

1. **只做派工單內的事**：派工單沒有明確要求的工作，一律不做。包括：順手修改看起來不對的東西、自行優化相關文件、補強「感覺缺少」的功能。
2. **禁止自行重構規範文件**：除非派工單明確指定 `job_type: docs_ops` 且目標是修改規範文件，否則不得更動 `docs/` 下任何準則文件。
3. **遇到範圍外問題，回報而非自行處理**：執行中發現問題但超出派工單範圍時，記錄在 Report 的「遺留問題」欄位，等待下一個派工單處理。
4. **遇到無法完成的步驟，停止並說明**：不得假裝完成、用模糊的句子掩蓋，必須明確說明「步驟 N 無法完成，原因是 ___」。

## 第五章：花費回報統一格式

**所有文件（JOB 派工/結案/對話回應）統一使用此格式**：

```
## 真實回報本次對話的模型與花費
＄作業匯總 ：Token數:{真實Meta中數字} | 花費: ${換算台幣} | 使用模型: {真實Meta中的模型代碼} | 執行者: {AG|Cursor|Claude}
```

### 5.1 落實與回補機制
為解決「產出當下無法預知最終花費」之技術限制，回報流程應嚴格依循以下兩大情境：

**情境 A：單一 / 一次性任務**
- 若平台/環境 Context 內（或指令上文中）能夠讀取到**前次/本次對話**的真實耗用 Meta，Agent **必須主動讀取，並直接寫回前次的任務檔案或結果中**。
- 若環境嚴格無法取得，當下產出文件時先填入 `-`，由使用者決定是否補回。

**情境 B：大型多任務 JOB (跨多輪對話)**
- 在執行單一子任務途中，**不需要**每次都寫出總花費，可暫以 `-` 佔位。
- 等到該 JOB 所有的子任務皆完成並產出結案報告（Report.md）時，若系統有提供彙總或使用者主動提供，再於結案時進行一次性的統計寫回。

### 5.2 計價基準
- 花費換算依據相對應的**資料查詢時間**：**`../Model_Price.json`**（與本倉庫同層之 `0_AI_Project` 目錄；未納入本 repo 版控）之單價表；若該檔為 `.md` 舊版，以實際存在之檔為準。
- 若 Meta 真的無法取得，欄位顯示 `-`，**嚴禁推估與亂造數字**。

### 5.3 執行時間回報（例行統計）

**格式**（Report.md 強制填寫，派工單選填）：

```
## ⏱️ 執行時間回報
| 子任務 / 階段 | 開始時間 | 結束時間 | 耗時（分鐘） | 備註 |
| {子任務名}   | HH:mm    | HH:mm    | {N}          |      |
| **總計**     | —        | —        | **{N}**      |      |
```

**取得時間的優先順序**：
1. **Claude Code**：環境無法取得壁鐘時間，填 `-` 並在備註說明「Claude Code 環境限制」。
2. **Cursor / AG**：可於執行前後記錄系統時間（`date +%H:%M`），填精確值。
3. **用戶補回**：若執行者無法取得，用戶可於結案時補填 `last_updated` 對應的時段。

**禁止行為**：推估或捏造時間數字。填 `-` 比捏造更誠實。

**統計目的**：協助 PM 評估任務複雜度與 Agent 效率，作為未來派工規模預估的參考基準。

## 第八章：AG 執行守則（Antigravity 適用，其他 Agent 同樣適用）

本章是從過去任務失誤中歸納出的具體行為規範。不是建議，是必須遵守的規則。

### 8.1 報告品質規則

| 禁止行為 | 正確做法 |
|:--|:--|
| 「已完成所有需求」 | 列出實際完成了哪些步驟，每步有具體產出 |
| 「歷史變更，已合併於 Main」 | 列出每一個實際修改的檔案完整路徑 |
| 「測試通過（免除補測）」 | 說明用什麼方式驗證、結果是什麼 |
| 「待確認」作為遺留問題 | 說明具體問題是什麼、建議如何處理 |
| Checklist 全部打勾但無佐證 | 每個驗收項旁邊填入實際數值或操作結果 |

### 8.2 範圍控制規則

執行任務時，遇到以下情況必須停止並回報，不得自行決定：

- 發現規範文件有問題 → 寫進「遺留問題」，不自行修改
- 發現相關程式碼有問題 → 寫進「遺留問題」，不順手修復
- 任務步驟中有一步無法完成 → 說明原因，等待指示，不跳過或假裝完成
- 發現派工單的範圍比預期大 → 回報後等確認，不擅自縮減或擴大

### 8.3 溝通規則

- 不確定要怎麼做：問，不要猜
- 發現矛盾的規範：回報矛盾，等待裁定，不自行選擇一個版本
- 任務完成但沒把握：在 Report 的「技術筆記」說明不確定的部分
- 任何「我覺得」「應該」的判斷：先問，再做

### 8.4 花費誠實規則

- 若無法取得 Token 數與花費，欄位填 `-`
- 禁止填入估算值、猜測值
- 禁止省略花費欄位

## 第九章：文件設計原則（Documentation Architecture）

> **設計背景**：本章原則參考 Claude Code 源碼的 prompt 分層架構（Static/Dynamic Boundary）、GitHub Spec Kit 的階段式文件方法論（Specify → Plan → Tasks → Implement）、Andrew Ng 的 Agentic Design Patterns（Reflection / Planning），以及多篇 Claude Code prompts.ts 逆向分析文章的 Mechanism vs Policy 概念。目的是讓 Agent 與人類協作時，文件系統不會因為重複、模糊、膨脹而崩塌。

### 9.1 核心心法：每份文件只做一件事

| 原則 | 說明 | 違反徵兆 |
|:--|:--|:--|
| **單一職責** | 一份文件負責一個主題，寫清楚自己「管什麼」和「不管什麼」 | 同一份檔案同時講出題規則和研究方法 |
| **單點維護** | 每個知識點只在一處維護正文，其他地方只放指標連結 | 兩份文件都列了考古題來源清單，改了一份忘了另一份 |
| **文件定位宣告** | 每份文件開頭必須有一行 `文件定位`，聲明邊界與排除範圍 | 讀者不確定「這個規則到底寫在哪裡」 |

**實作方式**：
- 開頭寫：「本文件負責 ___，不負責 ___（見 `{另一份檔案}`）」
- 已有專屬文件的內容，本文只寫一行指標，例：`> 考古題來源與 SOP → knowledge/考古/README_考古題蒐集規範與來源索引.md`

### 9.2 三層資訊架構（Index → Summary → Detail）

受 Claude Code 記憶系統啟發——context 是稀缺資源，不該把所有規則一次倒進來。

| 層級 | 內容 | 載入時機 | 範例 |
|:--|:--|:--|:--|
| **索引層** | 一行指標（檔名 + 一句話描述） | 永遠載入（L0/L1） | CLAUDE.md 的文件索引表 |
| **摘要層** | 核心規則精華（≤ 30 行） | Hook 自動注入 | SessionStart 注入的通用準則精華 |
| **正文層** | 完整規範、範例、附錄 | 執行特定任務時才讀取（L2） | 各 README 正文 |

**設計規則**：
- 索引層的每一行必須在 150 字元內，超過就是正文洩漏到索引
- 摘要層只放「Agent 不讀就會犯錯」的規則，其餘留在正文
- 正文層可以很長，但讀者應能透過索引找到入口，不需要通讀全文

### 9.3 靜態規則 vs 動態內容（Boundary Separation）

Claude Code 的 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 告訴我們：**不變的東西和會變的東西必須分開放。**

| 類型 | 特徵 | 存放策略 |
|:--|:--|:--|
| **靜態規則** | 跨任務不變（角色分工、禁止事項、格式規範） | 寫入準則文件，由 Hook/L0 注入 |
| **動態狀態** | 隨任務改變（進度、版本號、當前執行步驟） | 寫入派工單、Report、進度表 |
| **衍生資料** | 可從程式碼或 git 推導出（檔案結構、最近 commit） | 不寫入文件，需要時即時查詢 |

**禁止行為**：
- 在準則文件中寫入會過期的狀態（如「目前 L2 有 7 題」）
- 在派工單中重複準則正文（應寫「依 §9.1 原則」而非複製貼上）
- 在文件中記錄可用 `git log` 或 `ls` 取得的資訊

### 9.4 What / Why / How 分離（Phase-Appropriate Detail）

參考 GitHub Spec Kit 的四階段方法論，不同文件回答不同問題：

| 文件階段 | 回答的問題 | 不該出現的內容 |
|:--|:--|:--|
| **規範文件**（README_*.md） | What：規則是什麼、Why：為什麼這樣規定 | 具體操作步驟、程式碼片段 |
| **派工單**（JOB-*.md） | What：這次要做什麼、邊界在哪 | 規範正文的複製貼上 |
| **SOP / Skill** | How：具體怎麼操作、步驟順序 | 長篇理論解釋 |
| **Report** | Done：實際做了什麼、數據佐證 | 計畫或未來展望 |

**檢驗方法**：如果一段文字同時在解釋「為什麼」和「怎麼做」，它應該被拆成兩份文件。

### 9.5 為 Agent 而寫（Agent-Readable Writing）

Agent 與人類閱讀方式不同。Agent 需要的是結構化的判斷依據，不是散文。

| 人類習慣 | Agent 需要 |
|:--|:--|
| 「注意品質」 | 「CQI-P ≥ 5.5 方可進入盲測」 |
| 「適當引用來源」 | 「每題標註：學校名稱 + 學年度 + 考試類型」 |
| 「不要抄太多」 | 「檢驗：把考古題原檔刪除後，這道題是否仍站得住腳」 |

**寫作守則**：
- 規則用可程式化的條件句（「若 X 則 Y」），不用模糊形容詞
- 每條規則附「違反時怎麼辦」——Agent 需要 fallback 路徑
- 包含 **Why**：Agent 遇到邊界案例時，理解原因比背誦規則更有用
- 禁止項明確列為表格或清單，不藏在段落敘述中

### 9.6 文件存活性（Compaction Survival）

Claude Code 的 context 壓縮機制會丟棄冗長內容，只保留結構化摘要。文件設計必須確保關鍵規則能在壓縮後存活。

**存活率高的寫法**：
- 表格（結構化，壓縮器傾向保留）
- 一行式規則（「每課 ≥10 題 + ≥2 來源」）
- 明確的數值門檻

**存活率低的寫法**：
- 長段落散文（壓縮器會摘要，細節丟失）
- 隱含在敘述中的規則（「一般來說最好能有多一點來源」）
- 沒有數值的軟性建議

### 9.7 文件修改紀律

| 情境 | 處理方式 |
|:--|:--|
| 發現文件 A 和文件 B 內容重複 | 保留一處正文，另一處改為指標連結 |
| 想在文件中加入新段落 | 先確認是否已有專屬文件負責該主題 |
| 規則已過時或被新決策取代 | 刪除舊規則，不加 `// deprecated` 或 `~~刪除線~~` 保留屍體 |
| 不確定該寫在哪份文件 | 問：「這段話回答的是 What/Why 還是 How？」→ 對照 §9.4 歸位 |
