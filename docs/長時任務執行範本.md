## 文件定位

本範本用於規劃與執行**長時、批次、有可量化 progress** 的任務。它不是函式庫，而是**設計+操作 SOP**：你要拷貝骨架、改 placeholder、依文件啟動五元件，就能讓任務在無人介入的情況下穩定跑數天並即時回報。

不適用：
- 一次性短任務（< 2 小時、無 batch、無 progress 概念 → 直接執行即可）
- 純前端/規範文件編輯（不需要 progress 追蹤）

---

## 一、適用情境（三條全中再啟用）

| 條件 | 判定方式 |
|:--|:--|
| **時長 ≥ 2 小時** | 序列執行+限速+人為等待累計 ≥ 2 小時 |
| **可拆 batch** | 任務由 N 個獨立子任務組成（N 個 drive、N 課、N 題、N 檔案）|
| **有可量化 progress** | 能在每個子任務結束後寫入「已完成 / 失敗」這類進度記錄 |

> **三條全中**啟用本範本。否則請考慮直接執行或用更輕量的工具。

## 二、五元件架構

```
┌──────────────────────────────────────────────────────────┐
│  ① Progress State（持久化 JSON / DB）                     │
│     - 每個 batch 結束立即寫入                              │
│     - 包含 status / 計數 / last_attempt / error_note       │
│  ↑ 寫入                          ↓ 讀取                    │
│  ┌────────────────────┐   ┌─────────────────────────┐    │
│  │ ② Worker（批次執行）│   │ ③ Dashboard（讀取顯示）│    │
│  │  + per-task timeout │   │  時間戳/增量/進度條/ETA │    │
│  └────────────────────┘   └─────────────────────────┘    │
│           ↑ 啟動                    ↑ 觸發                │
│  ┌────────────────────┐   ┌─────────────────────────┐    │
│  │ ④ Loop Wrapper（連續批次）│ ⑤ Wakeup + Discord     │    │
│  │   自動 batch、自動停止     │  1h 自動回報、Discord  │    │
│  └──────────────────────────┘ └────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

每個元件**單一職責**，互不替代。少一個都會在實際長跑時出問題。

## 三、五元件詳細設計

### ① Progress State — 持久化 JSON

**為什麼**：長時任務必然會中斷（網路斷、電腦休眠、子程序卡死、磁碟滿、人為打斷）。只要每個子任務做完都立即寫入持久化狀態，下次啟動腳本就能跳過已完成的，從中斷點繼續。

**怎麼做**：
- 用 JSON（陣列 of objects）即可，不用上資料庫
- 每筆至少有：`id`、`status` (`pending`/`done`/`partial`/`failed`)、`last_attempt`（ISO 時間戳）、`error_note`、`<task-specific count>`（已下載 PDF 數、已產出題數等）
- **每個子任務一結束立即寫入**（不要等整批結束）

**JOB-209 範例**：`knowledge/3_考古題/_manifest/download_progress.json`
```json
[
  {
    "priority": 1, "grade": "G3", "semester": "下學期",
    "subject": "國語", "publisher": "南一", "exam_type": "期中考",
    "url": "https://drive.google.com/...",
    "local_path": "knowledge/3_考古題/1_原始檔/三下/三下_國語_南一/",
    "expected_pdf_count": 26, "downloaded_pdf_count": 26,
    "status": "done",
    "last_attempt": "2026-04-26T03:15:42",
    "error_note": null
  }
]
```

**設計坑點**：
- ❌ 不要用「set-based 新增檔案數」決定 status（retry 重跑時會誤判為 0 → 降級 partial→failed）
- ✅ 用「manifest 預期清單 vs 實際存在比對」決定 status

---

### ② Worker — 批次執行 + per-task timeout

**為什麼**：第三方 API / 子程序常會卡住（gdown 內部 retry loop、Playwright headless 卡死、網路 long timeout）。沒有 hard timeout 一卡可以卡 4 小時不動。

**怎麼做**：
- 主路徑用最快的工具（如 gdown CLI）
- 主路徑失敗 → fallback 到備援工具（如 Playwright 模擬瀏覽器）
- **每個子任務包一層 hard timeout**（建議 25 min）：超過直接 kill 並標 failed

**JOB-209 範例**：`scripts/exam_download_runner.py`
- gdown CLI subprocess.run with `timeout=600`
- Playwright 在 main loop 套 `signal.SIGALRM` alarm 25 分鐘
- 超時自動切下一個子任務，不卡住整個 loop

**設計坑點**：
- ❌ 不用 module 模式直接呼叫第三方（沒辦法 timeout）
- ✅ 強制走 subprocess 才能用 OS 級 timeout
- ❌ Python signal.alarm 對 socket I/O 有時無效（macOS 上實測）
- ✅ 雙層保護：subprocess timeout + main loop alarm

---

### ③ Dashboard — 即時進度儀表板

**為什麼**：回報如果只說「還在跑」對使用者沒意義。要讓使用者隨時能看到「**現在到哪、速率多少、預估什麼時候完成**」。

**怎麼做**：
腳本讀 progress JSON 印出：

```
╔══════════════════════════════════════════════════════════════╗
║  📊 任務進度儀表板                                           ║
║  🕐 回報時間：2026-04-27 (週一) 09:18:06                       ║
╚══════════════════════════════════════════════════════════════╝
  整體：done=352  partial=102  failed=9  pending=241
  完成度（done+partial）：454/704 = 64.5%

  近 30 分鐘增量：
    9 drives 處理 | done=7 partial=2 failed=0
    新增檔案：119 份 | 速率：4.0 檔/分

  各分組進度（依執行順序）：
  G3 下學期  ████████  98%
  G4 下學期  ████████  96%
  G5 下學期  ████████  95%
  ...
  G2 上學期  ░░░░░░░░   0%

  預估剩餘：803 min (13.4h)
  預估完成：2026-04-27 22:41
╚════════════════════════════════════════════════════════════╝
```

**必備元素**（六個都要有）：
1. **醒目時間戳**（含日期、星期、HH:MM:SS）
2. 整體狀態計數（done / partial / failed / pending）
3. 完成度百分比
4. **近 N 分鐘增量**（讓使用者看出「最近還在動」）
5. 分組進度條（依執行順序，不是依字母）
6. 預估剩餘 + 預估完成時間

**JOB-209 範例**：`scripts/progress_dashboard.py`

### ④ Loop Wrapper — 連續批次串接

**為什麼**：Worker 每次只跑一個 batch（30 個子任務）。Wrapper 自動串接：跑完一批 → 看還剩多少 → 跑下一批 → 直到 0 或無進展自停。

**怎麼做（shell wrapper）**：
```bash
batch_n=0
prev_remaining=-1
while true; do
    remaining=$(count_remaining 2>/dev/null || echo -1)
    if [ -z "$remaining" ] || ! [[ "$remaining" =~ ^-?[0-9]+$ ]]; then
        echo "count_remaining 失敗，等 60s 重試"
        sleep 60; continue
    fi
    if [ "$remaining" -eq 0 ]; then break; fi
    if [ "$prev_remaining" -eq "$remaining" ] && [ "$batch_n" -gt 0 ]; then
        echo "連兩輪沒減少，loop 結束"; break
    fi
    prev_remaining=$remaining
    batch_n=$((batch_n + 1))
    echo "=== Batch #$batch_n 啟動，剩 $remaining ==="
    python3 scripts/<worker>.py --batch 30
    sleep 120  # 批次間休息
done
```

**設計坑點**：
- ❌ 直接 `set -u` + `count_remaining` 失敗 → unbound variable crash 整個 loop
- ✅ 加 `2>/dev/null || echo -1` 防護 + 數字驗證
- ❌ 純 `while pending>0` → 健體那種「永遠 partial」會無窮迴圈
- ✅ 加「連兩輪沒進展自停」保護

**JOB-209 範例**：`scripts/continuous_download_loop.sh`、`scripts/continuous_retry_missing_loop.sh`

### ⑤ Wakeup + Discord — 自動定期回報

**為什麼**：沒人會盯著 terminal 看 6 小時。需要主動推進度給使用者。但也不能太頻繁（半小時一次太煩、5 分鐘一次無意義）。

**怎麼做**：
- 用 `ScheduleWakeup` tool 每 60 分鐘自動跑一次「dashboard + Discord 同步」
- prompt 模板（每次 wakeup 用一樣的）：
  ```
  回報順序：
  (1) 訊息開頭用粗體列出當下時間（**🕐 回報時間：YYYY-MM-DD (週X) HH:MM:SS**）
  (2) 跑 `python3 scripts/<dashboard>.py --since-minutes 60`
  (3) 算「實際完成量」（用真值比對）
  (4) 同步用 mcp__plugin_discord_discord__reply 送到 `eidos_派工與回報` (chat_id=`1487738477608177714`)
  (5) 確認 loop PID <PID> 是否還在跑
  (6) grep "<batch keyword>" <log path>
  (7) `df -h .` 看磁碟剩餘
  若 loop 結束就停止連續排程。
  ```

**Discord 訊息格式**：
```
📊 **<任務名> 進度回報**
🕐 回報時間：**2026-04-27 (週一) 14:09:05**

**整體**：done=389 / partial=135 / failed=11 / pending=169
**完成度**：524/704 = **74.4%** (+2.1pp / 60min)

**近 60 分鐘**：15 drives / 184 PDF / 3.1 檔/分

**各分組**：
（進度條）

**Loop**：PID xxx running, Batch #N 進行中
**預估完成**：YYYY-MM-DD HH:MM (剩 ~Nh)
```

**JOB-209 範例**：固定發到 `eidos_派工與回報`（`1487738477608177714`），由 `mcp__plugin_discord_discord__reply` 送出。

## 四、失敗模式與處置

過去 6 天 JOB-209 遇到的真實狀況都列於此，**遇到先對照**這張表處置：

| 症狀 | 真因 | 處置 |
|:--|:--|:--|
| **Loop 卡 4+ 小時無新 progress，process 還活著（SN 狀態）** | 第三方 module 無 timeout 進入內部 retry | 改 subprocess 模式 + 加 hard timeout |
| **Process 已停但 progress 看起來沒結束** | 子 process 被 OS 殺但 wrapper 沒偵測 | 加 PID 確認到 wakeup prompt |
| **大資料夾只下到前 50 個項目** | virtualized list（如 Drive C-WIZ 容器）只 render 可視範圍 | 操作前 JS scroll 容器到底，反覆直到無新項目 |
| **partial 重跑變 failed（降級）** | set-based「新增 = 0」誤判 | 改用「真值 vs 預期清單比對」決定 status |
| **網路斷線後 wrapper 整個崩** | shell `set -u` + count 函式 fail = unbound variable | wrapper 加 `\|\| echo -1` + 數字驗證 |
| **電腦休眠 1 小時** | 物理事件，process 一起暫停 | 不用處理（醒來自動續），但 wakeup 偵測「N 小時無進度」時要先看 process 是否還活著再判定 |
| **磁碟滿（97%+）** | 累積 zip 暫存 + 子 cache | 計算階段就警示（dashboard 加 `df -h` 監測）+ 通知使用者清理或搬走 |
| **使用者中途改目錄結構** | 整理需要 | 停 loop → 改 worker 路徑邏輯 → 改 progress.json local_path → 重新驗算 → 重啟 loop |
| **某類子任務永遠 fail（如健體子目錄）** | 工具能力外限制 | 標 `error_note` 含「需手動處理」關鍵字 + worker/wrapper 跳過此標籤 |
| **同一資料兩種命名版本混雜** | 用戶整理過後與工具下載命名不同 | 不要 rsync 直接合併（會雙存），用 hash 比對去重；或保留兩種命名並接受 |

## 五、30 分鐘套用 Checklist

接到符合「適用情境」的長時 JOB 後：

| # | 動作 | 預估時間 |
|:--|:--|:--|
| 1 | 拷貝 `scripts/templates/progress_dashboard.py` 改成 `scripts/<task>_dashboard.py`，改 progress JSON 路徑、grouping key、近期增量計算欄位 | 5 min |
| 2 | 拷貝 `scripts/templates/continuous_loop.sh` 改成 `scripts/continuous_<task>_loop.sh`，改 `count_remaining()` 函式、worker 指令、log 路徑 | 5 min |
| 3 | 確認 worker 腳本有 per-task hard timeout（subprocess timeout + main loop signal.alarm 雙層）；沒有就先加 | 10 min |
| 4 | 啟動 loop（背景跑），記下 PID 與 log 路徑 | 1 min |
| 5 | 用 ScheduleWakeup 排第一次 wakeup（60 分鐘後），prompt 用 `scripts/templates/wakeup_prompt.md` 模板 | 2 min |
| 6 | 第一次手動發 Discord 通知「任務啟動」 | 2 min |
| 7 | 把任務的 PID / log path / dashboard 路徑記在 JOB Report 草稿 | 2 min |

之後 wakeup 會自動跑 dashboard + Discord 同步，使用者只要看 Discord 就能掌握進度。
